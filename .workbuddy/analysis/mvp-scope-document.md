# EcoMind OS MVP 范围文档

> 基于《创始人手册》Ch4 推荐动作1（先写架构上下文）、推荐动作2（先写范围文档）、推荐动作6（向证据迭代）

---

## 一、MVP 定义

### 一句话描述

> 为环境监测站运维人员提供一个**AI驱动的数据异常智能预警与研判助手**，自动发现监测数据异常、智能研判原因、推荐处置方案。

### 为什么选这个场景

| 评估维度 | 得分 | 理由 |
|---------|:----:|------|
| 问题频率 | 高 | 监测数据异常几乎每天发生 |
| 痛点强度 | 高 | 异常漏报/误报直接影响考核和决策 |
| 数据可获得性 | 高 | 国控/省控监测数据已有成熟API和数据接口 |
| 技术可行性 | 高 | 时序数据分析+规则引擎是成熟技术，LLM辅助研判已有先例 |
| 商业验证速度 | 高 | 单个监测站即可试点，不需要全局部署 |
| 扩展潜力 | 高 | 成功后可扩展到执法、环评等场景 |

### 用户故事

**作为** 一名环境监测站运维工程师，
**我希望** 系统能自动检测我负责的监测站点数据异常，
**并且** 智能分析可能原因（设备故障/污染事件/气象影响/质控问题），
**同时** 推荐对应的处置步骤，
**以便** 我能从"盯数据+排异常"的日常工作中解放出来，把精力放在真正需要人工判断的事件上。

## 二、MVP 做什么（In Scope）

### 核心功能（Must Have）

| # | 功能 | 描述 | 验收标准 |
|---|------|------|---------|
| F1 | 数据接入 | 接入至少1个监测站点的实时数据（空气/水质任选） | 数据延迟<5分钟，准确率100% |
| F2 | 异常检测引擎 | 基于规则+统计模型的自动异常检测 | 误报率<20%，漏报率<5%（与人工比对） |
| F3 | 智能研判 | LLM分析异常原因，给出Top3可能原因及置信度 | 研判准确率>60%（Top3命中） |
| F4 | 处置推荐 | 针对每种原因类型推荐标准处置步骤 | 覆盖≥5种常见原因类型 |
| F5 | 预警通知 | 异常发现后通过站内消息+邮件通知 | 通知延迟<10分钟 |
| F6 | 数据仪表盘 | 展示监测数据趋势、异常标记、处置状态 | 页面加载<3秒 |

### 辅助功能（Should Have）

| # | 功能 | 描述 |
|---|------|------|
| F7 | 历史回溯 | 查看过去30天的异常记录和处置结果 |
| F8 | 反馈闭环 | 用户可对AI研判结果点赞/踩，提供正确原因 |
| F9 | 简单报表 | 周/月异常统计报表导出 |

## 三、MVP 不做什么（Out of Scope）

### 明确排除

| 排除项 | 排除理由 | 何时考虑 |
|--------|---------|---------|
| 其他11个业务域 | 手册Ch4警告"零摩擦范围蔓延" | PMF验证后，按用户需求优先级逐一扩展 |
| L3 OS贯通（设备控制） | MVP阶段不需要直接控制物理设备 | 发布阶段，当安全合规达标后 |
| L4 认知记忆层（完整实现） | 长期记忆和学习循环是规模化能力 | 发布阶段后期 |
| L5 安全审计（完整实现） | MVP为内部试点，不需要企业级安全 | 发布阶段，面向外部客户前 |
| 真实设备对接（EMQX/OPC UA） | MVP用API数据接入即可 | 当需要对接非标准化设备时 |
| 数字孪生可视化（Cesium.js 3D） | MVP用2D图表即可满足 | 当用户明确需要空间可视化时 |
| 多租户/多组织支持 | MVP只服务1-2个试点站点 | 发布阶段 |
| 移动端APP | MVP做Web端即可 | 用户明确要求移动端时 |
| K8s部署 | Docker Compose即可满足MVP需求 | 生产流量达到需要水平扩展时 |

## 四、MVP 技术架构（精简版）

### 架构原则

手册Ch4推荐动作1：*"在打开编码代理前，定义架构原则、避免的依赖、阶段性取舍和六个月内的真实规模预期。"*

| 原则 | 说明 |
|------|------|
| 只用L1+L2 | 路由编排+Agent沙箱，L3-L5仅做接口预留 |
| 单Agent模式 | MVP只有一个"监测分析Agent"，不做多Agent协作 |
| 数据优先 | 先确保数据管道可靠，再优化AI研判 |
| 最小依赖 | 不引入K8s、不引入消息队列（MVP用直接调用） |
| 可观测 | 所有Agent决策留日志，便于复盘和改进 |

### 架构图（文字描述）

```
┌──────────────────────────────────────────────────┐
│                   前端 (React)                     │
│  数据仪表盘 | 异常列表 | 研判详情 | 处置跟踪        │
└──────────────────────┬───────────────────────────┘
                       │ REST API
┌──────────────────────┴───────────────────────────┐
│              L1 路由编排层 (Python/FastAPI)        │
│  API Gateway | 请求路由 | Agent调度 | 认证鉴权      │
└──────┬───────────────────┬───────────────────────┘
       │                   │
┌──────┴────────┐  ┌───────┴───────────────────────┐
│ L2 异常检测    │  │ L2 AI研判Agent                 │
│ 规则引擎       │  │ LiteLLM → Prompt模板 → 原因分析 │
│ 统计模型       │  │ 处置推荐 | 置信度评估           │
└──────┬────────┘  └───────┬───────────────────────┘
       │                   │
┌──────┴───────────────────┴───────────────────────┐
│              数据层                                │
│  PostgreSQL (监测数据+异常记录+用户反馈)            │
│  Redis (缓存+实时数据缓冲)                         │
│  pgvector (历史异常模式向量检索，预留)               │
└──────────────────────────────────────────────────┘
       │
┌──────┴───────────────────────────────────────────┐
│  外部数据源 (Mock/API)                             │
│  监测站数据API | 气象数据API | 排污许可数据API      │
└──────────────────────────────────────────────────┘
```

### 接口预留（L3-L5 Stub）

| 层级 | 预留接口 | 说明 |
|------|---------|------|
| L3 | `IDeviceConnector` | 设备数据接入的标准接口，MVP用API实现，未来可切换到EMQX |
| L3 | `ISpatialRenderer` | 空间数据渲染接口，MVP返回2D数据，未来可接入Cesium 3D |
| L4 | `IMemoryStore` | 记忆存储接口，MVP用PostgreSQL，未来可接入Hermes记忆系统 |
| L4 | `IKnowledgeGraph` | 知识图谱查询接口，MVP用规则表，未来可接入Neo4j |
| L5 | `IAuditLogger` | 审计日志接口，MVP写文件日志，未来可接入企业级审计系统 |
| L5 | `IApprovalWorkflow` | 审批流程接口，MVP跳过，未来可接入Temporal工作流 |

## 五、成功标准（PMF信号）

手册Ch4退出标准：*"出现真正的产品-市场匹配证据：留存、收入、推荐或其他能证明特定用户群持续获得价值的信号。"*

手册Ch4常见风险警告：*"早期热度不是PMF；朋友使用、投资人资源导流、榜单曝光都可能只是短期噪声。"*

### 定量标准

| 指标 | 目标值 | 数据来源 |
|------|--------|---------|
| 试点用户数 | ≥5个监测站运维人员 | 注册/邀请记录 |
| 周活跃率 (WAU/MAU) | ≥60% | 后台使用日志 |
| 日均使用次数 | ≥3次/活跃用户 | 功能调用日志 |
| 异常研判采纳率 | ≥50%（用户对研判结果认可/采纳） | 反馈数据 |
| D7留存 | ≥40% | 使用日志 |
| D30留存 | ≥20% | 使用日志 |
| NPS | ≥30 | 定期问卷 |

### 定性标准

| 信号 | 判断方式 |
|------|---------|
| 用户主动推荐 | ≥1位用户向同事主动介绍/推荐使用 |
| 用户主动要求新功能 | 用户提出"能不能再加一个..."的具体需求（非泛泛而谈） |
| 用户愿意付费 | 至少1个试点单位表示"如果正式上线，我们愿意付费" |
| 用户无法回到旧方式 | 用户表示"用了之后回不到以前的方式了" |

## 六、迭代条件（什么时候可以扩大范围）

手册Ch4推荐动作2：*"明确MVP做什么、不做什么，以及什么样的用户证据才允许新增功能。"*

| 条件 | 触发动作 |
|------|---------|
| WAU ≥60% 且 D7 ≥40% 持续4周 | 可以开始第二个场景的设计调研 |
| ≥3个试点单位签署付费意向 | 可以开始商业化准备 |
| 用户主动提出≥5个具体新功能需求 | 可以评估其中1个纳入MVP+ |
| 研判采纳率 ≥70% 持续2周 | 可以开始扩展到第二个业务域（执法监察）的调研 |
| 任何指标连续2周下降 >20% | 暂停扩张，诊断问题（可能是假性PMF） |

## 七、3个月里程碑

### Month 1：数据管道 + 基础Agent

| 周 | 里程碑 | 交付物 |
|----|--------|--------|
| W1 | 项目初始化 + 数据接入 | 数据库Schema、API对接、Docker Compose配置 |
| W2 | 异常检测引擎 v1 | 规则引擎 + 简单统计模型上线 |
| W3 | AI研判Agent v1 | LiteLLM集成、Prompt模板、基础研判功能 |
| W4 | 内部测试 + 修复 | 使用模拟数据完成端到端测试 |

### Month 2：预警工作流 + 用户界面

| 周 | 里程碑 | 交付物 |
|----|--------|--------|
| W5 | 预警通知系统 | 邮件/站内消息通知 |
| W6 | 前端仪表盘 v1 | 数据展示 + 异常列表 + 研判详情 |
| W7 | 反馈闭环 | 点赞/踩 + 原因纠正功能 |
| W8 | UAT（用户验收测试） | 邀请2-3个目标用户试用 |

### Month 3：用户测试 + 迭代

| 周 | 里程碑 | 交付物 |
|----|--------|--------|
| W9 | 用户测试 Round 1 | 收集反馈、分析使用数据 |
| W10 | 迭代优化 | 基于R1反馈修复和优化 |
| W11 | 用户测试 Round 2 | 验证改善效果 |
| W12 | MVP评估报告 | 判断是否达到PMF信号、决定下一步方向 |
